## 背景

TikTok 私信「火花」功能自上线以来业务规模快速增长，用户渗透率超过 16%，触达用户超过 2 亿。伴随高速发展，线上事故一度频发，用户反馈长期居高不下。火花前后端团队从全局视角审视架构短板，对数据链路与系统架构进行了重构并取得显著成效：用户相关反馈量从年初的日均上千例降至目前的不足 100 例。

本文从**服务端架构优化**角度说明我们如何提升系统稳定性与用户体验。结合火花业务特点，我们利用幂等与 CRDT 思想巧妙解决了多机房数据同步的一致性难题，并形成可复用的方法论，供其他业务参考。

## 火花业务介绍

火花通过「🔥 + 数字」记录好友间的连续私信天数，以游戏化方式激励用户保持互动。

**核心玩法**

- 连续 3 天完成双向私信互动，即可解锁火花。
- 每天 00:00 火花变为灰色，当天完成双向互动后重新点亮为橙色，天数 +1。
- 当天未完成双向互动，火花当日熄灭。
- 火花熄灭后，用户有 48 小时恢复窗口，超时则火花永久消失，已累积天数清零。

### 业务特点

- **资产属性：** 火花已成为用户重要的社交「资产」。此类资产的损失容忍度极低，系统短时不稳定或容灾不足都会显著影响体验，带来集中投诉并损害长期价值。
- **沉没成本高：** 玩法依赖持续稳定体验。若火花异常中断，需重新解锁且已累积天数被重置，严重打击用户继续累积的意愿。
- **反馈波动多：** 等级越高，用户反馈倾向越强。系统故障、站内误导性视频传播、新功能上线等因素交织，导致反馈波动频繁，归因复杂。

### 稳定性建设的必要性

- 火花相关用户反馈一度日均 1000+ 例，其中 Bug 类占比超过 40%。
- 曾在一个月内出现 3 次严重事故，导致大面积用户体验受损。
- 提升数据一致率是后续产品迭代与衍生玩法的基石。

> 反馈口径为离线反馈，Bug 类反馈包含 Bug 反馈和疑似 Bug 反馈

## 架构 1.0 概览

**架构特点（1.0）**

- 全球多机房部署，包含 ROW、EUTTP、USTTP 三个 vGeo，满足合规要求。
- 业务基于消息系统，上层依赖 IMCloud 的跨机房同步，会话消息在合规机房重放（replay）。
- 每个机房为独立集群（计算与存储单元），机房间不直接通信。
- 后台通过命令消息 push 通知客户端火花状态变更。
- 通过离线脚本每日全量扫描与修复，提升多机房数据一致率。

火花 1.0 支持了业务的快速迭代，同时其优缺点亦较为明显：

**优点**：

- 架构简单，多机房数据同步完全依赖 IMCloud，无额外同步链路。
- 机房相互独立，若无异常，最终计算结果理论上保持一致。
- 对只执行一次的逻辑（如发送续火消息），校验 `IsReplay` 标记，仅在原机房执行。
- 消息作用域由 IMCloud 控制，只在会话所属机房重放，存储范围满足合规要求。

**缺点**：

- 从 IMCloud 到存储写入链路较长，任一环节不一致均可能导致最终数据不一致（如 IMCloud 重放异常、MQ 阻塞、下游失败/返回不一致、写存储失败）。
- 同步链路单一，强依赖 IMCloud；一旦 IMCloud 异常，业务直接受影响，容灾弱。
- 依赖消息 `IsReplay` 标记无法实现 exactly-once 语义，边界 case 较多。
- 离线修复不可靠：
  - 无 Single Source of Truth，只能对多机房取 max 值以避免用户体验受损，易造成天数异常增长。
  
    $$\vec{v}=max\{\vec{v_1}, \vec{v_2}, ...,\vec{v_n}\}=max\{\begin{bmatrix}
       v_{1a} & v_{2a} & ... & v_{na} \\
       v_{1b} & v_{2b} & ... & v_{nb} \\
       ... & ... & ... & v_{na} \\
       v_{1m} & v_{2m} & ... & v_{nm}
    \end{bmatrix}\} = \begin{bmatrix}
    max\{v_{1a}, v_{2a}, ..., v_{na}\} \\
    max\{v_{1b}, v_{2b}, ..., v_{nb}\} \\
    max\{...,\  ...,\  ...,\  ...\}\\
    max\{v_{1m}, v_{2m}, ..., v_{nm}\}
    \end{bmatrix}$$
    
  - 离线工具需全表扫描、逐机房比对，常耗时半天以上，且非实时，修复后一致率仅 96% 左右。

### 存储结构（1.0）

使用 Redis String 存储火花数据，key 为火花 ID，value 为序列化的 protobuf 结构（StreakValue）：

```protobuf
message StreakUser {
  int64 uid = 1;
  int64 timestamp = 2; // The timestamp of user's last message
}

message StreakValue {
  repeated StreakUser users = 1;
  int32 streak_counter = 2; // The total days of this streak
  string streak_timezone = 3;

  // skip other fields
  // ...
}
```

该结构既用于存储亦用于前后端协议，且**前后端使用同样算法计算火花状态**。

### 火花状态计算要素（1.0）

- 用户 A、B 最近一条消息时间：$t_a,\ t_b$
- 当前时间：$t_{now}$
- 火花时区：$tz$

基于 $t_{now}$ 与 $t$ 可得到当前时区下昨天与今天的时间戳区间，火花状态判断逻辑如下：

- $t_a,\ t_b$ 均在今天，则火花点亮。
- 若二者均在昨天或其一在今天，火花变灰。
- 其他情况，火花消失。

### 潜在问题（1.0）

**问题列表**

- **写操作原子性无法保证：** 多机房并发写时，两个用户同时发消息容易相互覆盖。
- **必须保证有序消费：** 存储仅记录最近一条消息时间，若先消费 T1 日消息再消费 T0 日消息，会导致状态回退。
