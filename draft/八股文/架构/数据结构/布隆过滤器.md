## 一、从案例入手

### 案例1：用户激活态查询

假设有1亿个用户账号，每个账号在DB中存储一条激活的数据。当用户处于激活状态时，请求返回相应数据；否则返回空数据。

为了应对这种高QPS的查询请求，可以采用简单的架构设计，即引入Redis作为缓存。我们持续维护热点数据到Redis中，当Redis缓存未命中时才向DB发起请求。

### 案例2：黑名单过滤（CQC场景下可以类比为文件的MD5数据，是否已经标注）

在经典的黑名单业务场景中，服务维护了一个userId黑名单，要求拦截所有命中黑名单的用户。考虑到当前业务的高QPS（例如网关场景），在数据源确定的情况下，可以采用非常简单的架构设计。

### 如果在高QPS和高数据量下会有什么业务瓶颈？

假设有10W的QPS和1亿的数据量，我们可能会遇到一些常见问题：

1. **Redis的数据容量问题**：Redis是否能够存储如此庞大的数据量，尤其是在数据量激增时（例如大促活动）。
2. **Redis宕机引发的雪崩效应**：当Redis宕机时，可能会导致大量请求集中到数据库，特别是处理大量冷数据时。
3. **热点key穿透问题**：热点key被大量请求命中，导致请求直接穿透到数据库，增加数据库负载。
4. **高QPS下的Redis请求量问题**：高QPS情况下，Redis能否承受如此大量的请求，是否会出现性能瓶颈。

除此之外，还有其他可能导致服务质量下降的场景，例如：

1. **黑白名单过滤**：处理大量的黑白名单过滤请求可能会影响服务性能。
2. **去重操作**：需要对请求进行去重操作，可能导致额外的性能消耗。
3. **数据库空查询**：处理数据库中没有数据的查询请求，也会占用系统资源。
4. **可能出现的穿透场景**：例如缓存穿透、数据库查询穿透等情况，都可能影响服务的稳定性和性能。

这些问题本质上反映了采用Cache+DB架构下高QPS请求常遇到的问题：**大量无效的请求和判断处理占用资源，影响服务质量和性能**。

## 二、常规方案对比

*以用户激活态为例*

### 1. 使用Redis

注意需要考虑网络延迟，但是对应用服务器内存要求较低。

假设业务总体有1亿条数据，同时假设只存储userId，单个userId长度为10，加上业务前缀"TEST_ByteDance_USER_ID_"

选用Redis，可以预估下存储总共耗费的空间：

![Redis内存计算](布隆过滤器/image_redis_memory.png)

> 按1亿数据进行计算：80字节 * 1亿 / 1024 / 1024 / 1024 = 占用内存 **6.7G** 左右。

如果想提升性能，最简单的方法是在启动时进行初始化，在内存中存储全部数据，这样可以减轻对Redis的压力，但会增加应用的内存压力。

### 2. 将数据写入内存

#### 使用Golang的map结构

测试一下内存占用情况：

```go
func Test_Cache(t *testing.T) {
    cache = make(map[string]bool, 0)
    base := 100000000
    for i := 0; i < 100000000; i++ {
       key := base + i
       cache["TEST_dance_USER_ID_"+string(rune(key))] = true
    }
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("Total allocated memory: %d bytes\n", m.TotalAlloc)
}
```

数据打印情况：

```
RUN
Test_Cache
Total allocated memory: 2400208304 bytes
--- PASS: Test_Cache (2.90s)
```

也要占用**2G**的内存，这个对于单机服务是不可接受的。

#### 使用JAVA的MAP结构

```java
public static void main(String[] args) {
    Map<String, Boolean> cache = new HashMap<>();
    final int base = 100000000;
    for (int i = 0; i < 25000000; i++) {
        // 注意：这里我们减少了循环次数以避免消耗过多内存
        int key = base + i;
        cache.put("TEST_dance_USER_ID_" + key, true);
    }
    System.out.println("finish:" + cache.get("TEST_dance_USER_ID_100000001"));

    // 获取JVM的内存使用情况
    Runtime runtime = Runtime.getRuntime();
    long totalMemory = runtime.totalMemory(); // JVM试图使用的总内存量
    long freeMemory = runtime.freeMemory();   // 尚未使用的内存量
    long usedMemory = totalMemory - freeMemory; // 已使用的内存量
    System.out.println("Total memory: " + totalMemory / 1024 / 1024 + " MB");
    System.out.println("Free memory: " + freeMemory / 1024 / 1024 + " MB");
    System.out.println("Used memory: " + usedMemory / 1024 / 1024 + " MB");
    // 注意：这里获取的是JVM层面的内存使用情况，而非Java对象占用的精确内存大小
}
```

数据打印情况：

```
Total memory: 4758 MB
Free memory: 1575 MB
Used memory: 3182 MB
```

#### 综上

常规的 HashMap 和 Redis 虽然能够准确过滤数据，而且效率很高，时间复杂度都是 O(1)，但是会占用各自的机器较高的内存，对于单机服务来说是不可接受的。因此，这种情况下可以考虑使用**布隆过滤器**。

## 三、布隆过滤器

### 1. 基本概念

#### 简介

布隆过滤器（Bloom Filter）是一种由布隆在1970年提出的数据结构，它实际上是一个**二进制向量**和**一系列随机映射函数**组成。布隆过滤器的主要特点是高效的插入和查询，用于检索一个元素是否在一个集合中。

**可视化web页面**：[https://www.jasondavies.com/bloomfilter/](https://www.jasondavies.com/bloomfilter/)

布隆过滤器采用了哈希的方式进行查询，查询复杂度是 O(k)（k是哈希函数的个数），但在内存方面做了大幅优化，可以显著降低内存占用。

一个初始化的布隆过滤器，就是初始化一个bitmap：

（bitmap介绍：[https://blog.csdn.net/qq_29119581/article/details/115270409](https://blog.csdn.net/qq_29119581/article/details/115270409)）

![Bitmap初始化](布隆过滤器/image_bitmap.png)

随机映射函数，就是采用不同的hash算法，来对存储的key做hash。

假设设置三种hash函数：hashFunc1、hashFunc2、hashFunc3。

| **对于第一个key：byte** | **例如有第二个key：dance** |
|---|---|
| hashFunc1("byte") = 2 | hashFunc1("dance") = 1 |
| hashFunc2("byte") = 8 | hashFunc2("dance") = 8 |
| hashFunc3("byte") = 6 | hashFunc3("dance") = 6 |

![Hash函数示例](布隆过滤器/image_hash_example.png)

那么此时，下标1是0，那么说明布隆过滤器中必然是没有dance的。

### 2. 误判

可以观察到，尽管 1 没有命中，所以判定 "dance" 不存在，但 6 和 8 都是命中的。这是不可避免的，因为存在哈希函数，就存在哈希碰撞的可能性。

因此，在最糟糕的情况下，一个键的所有哈希函数执行结果恰好与**其他多个键的部分哈希函数发生碰撞**，这时就会出现误判。

假设此时布隆过滤器里有byte和dance，那么此时有key：toutiao

- hashFunc1("toutiao") = 1：和dance碰撞了
- hashFunc2("toutiao") = 2：和byte碰撞了
- hashFunc3("toutiao") = 6：和dance、byte都碰撞了

![误判示例](布隆过滤器/image_false_positive.png)

### 3. 布隆过滤器的概率特性

综上，由于布隆过滤器使用了哈希函数，因此它是一种概率性数据结构，可能存在一定的误判率。具体表现为：

1. **如果一个键命中了布隆过滤器，那么该键可能存在于布隆过滤器中。**
2. **如果一个键没有命中布隆过滤器，那么该键一定不在布隆过滤器中。**

还有以下特性，布隆过滤器并不是完全准确的。布隆过滤器误判的概率受到位图长度和哈希函数数量的影响：

1. **位图长度越长**，哈希函数的命中率就越低，但会浪费更多空间。
2. **哈希函数的数量越少**，位图的填充速率就越低，但哈希碰撞的几率就越高。
