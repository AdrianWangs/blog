## 缘起

- **"上下文工程（Context Engineering）"** 的术语概念最早可以追溯到 2025 年 6 月 19 日，Shopify CEO [**Tobi Lutke**](https://x.com/tobi/status/1935533422589399127) 在 X 上发送的一条推文，他认为该术语比**"提示词工程（Prompt Engineering）"**更贴切地描述向大语言模型提供全面背景信息的技能。
- 随后，AI 大神 [**Andrej Karpathy**](https://x.com/karpathy/status/1937902205765607626) 立即转发了该条推文，并附上**"+1"**，强调他也更喜欢"上下文工程"这个说法，而非"提示词工程"，该条转发立即引发轩然大波，截止至 2025 年 7 月中旬已经被**阅读了 210 万次**。

在笔者看来，上下文工程并**没有包含新的技术**，而是将过去 LLM 业界共识的应用技术栈**"新瓶装旧酒"的**打包起来组成一个新概念。毕竟在过去，Karpathy 一人就带火了**"Vibe Coding"**、**"LLM 操作系统"**、**"软件 2.0"**等概念。

然而这并不影响笔者**高度赞同两位前辈的看法**。其实自 2022 年大语言模型问世以来，我们就一直面临着**"如何让模型更好地获得与当下任务相关的信息"**这一核心挑战。无论是早期的**提示词（Prompt Engineering）**捞取最佳咒语，还是后来的**检索增强生成（RAG）**、**记忆体（Memory）**、**工具（Tool）、MCP、A2A** 集成等，各项技巧实际上都环绕着**"如何填充上下文"**这个主线不断进化，对于长期和 LLM 应用打交道的开发者来说，一定会对 Karpathy 补充的话题深有体会。

## 前世今生

> 可视化演示：[Transformer Explainer by PoloClub](https://poloclub.github.io/transformer-explainer/)

如 [Transformer Explainer](https://poloclub.github.io/transformer-explainer/) 所示，这是一个**直接运行在本地浏览器中**的 [**OpenAI GPT-2 开源模型**](https://github.com/openai/gpt-2)，你可以可视化的观察大语言模型的生成。GPT-2 和今天你使用的任何大模型一样都基于 Transformer 架构，均属于**"Token by Token"**逐字生成内容的**生成式 AI**。其输入是文本经过分词后的 Token 序列（即上下文）并进行向量化，而模型根据当前上下文预测下一个最有可能出现的 Token，并依次生成后续内容。本质上是基于概率分布的自动补全，并没有什么神秘之处，而笔者在界面顶端**最初输入**的 **`LLM is a`** 就是**"上下文"**。

当然今天的大模型早已不再是一个 Token 接龙，输入的上下文包括 **System Prompt** 和 **User Messages**（含 User Prompt）。除了接受文本外，还支持更丰富的上下文形式，如**图片**和**工具**等。

一直以来 AI 工程师都在尝试各种方案，在相对**有限的上下文空间**中，放置**任务说明**、**用户问题**、**音视频**、**内外部知识**、**示例、返回格式**等信息，最终以 **System Prompt**、**Tools**、**User Messages** 列表以及 **Response Format** 等有限形式，并尽量保证**信息完整**、**大模型能懂**、**上下文窗口使用最少**。同样的原始信息，不同的消息组成结构、不同的文本格式和工具设计，都会最终产生完全不同的效果。

> 即便在今天大模型厂家争先恐后的推算出 128k、320k 甚至更长的上下文空间，你仍然需要尽可能得少用上下文的 tokens，从而让 LLM 集中注意力在关键指令和数据上。

1. **Prompt Engineering 阶段**：最初业界更多关注于如何组织提示词、调节 Few-shot 示例、设计输出格式等"静态"上下文注入方法。这个阶段寄希望于更高明的 Prompt 来驱动 LLM 达成更高质量的输出，但应对复杂、动态场景时乏力。
   > 直到今天，开发者也只能通过 prompt 来指挥 LLM 执行任务，是学习 LLM 的必备基础技能，因此强烈推荐你阅读我的这篇教程入门提示词工程。

2. **RAG 与 Memory 的引入**：随着 token 限制与"模型无长期记忆"问题凸显，检索增强生成（RAG）、内容分段 Summarization、对话记忆等能力成为 LLM 工业级应用的标配。与此同时，Embedding 技术、向量数据库、短/长期记忆缓存等组件日趋成熟，帮助模型实时摄取所需外部信息。
   > 本文将涉及这两个重点概念。

3. **工具集成与智能体（Agent）范式**：为进一步扩展 LLM 的功能边界，开发者将 API 调用、代码运行、插件系统整合进推理链路中。模型变得不仅仅"会写作"，还能够搜索、计算、自动多轮推理。LangChain 这样的框架逐步把这些"上下文组件化"标准化。
   > 有关工具和智能体，强烈阅读我的这篇教程入门。

4. **流程自动化与模块编排**：在应用逐渐大型化、流程复杂化后，如何高效协同检索、解析、工具调用、输出验证等模块，成了上下文工程的核心落地难题。Orchestration Layer（流程控制层）以及自动上下文压缩和选择策略应运而生。
   > 除了本文外，有关基于 LangChain 和 LangGraph 开发多智能体 Deep Research 应用，请阅读我的这篇进阶教程。

> **上下文工程并不是演进的终点，相反上述这 4 个阶段皆为它的重要组成部分。**

## 核心要素

| 要素 | 说明 |
|------|------|
| **Instructions / System Prompt（指令及系统提示词）** | AI 的**角色**、**风格**、**行为规范、限制**等基础设置。 |
| **User Prompt（用户提示词）** | 用户提出的问题、布置的任务或交流内容。 |
| **State / History（Short-term Memory，短期记忆）** | 当前正在进行的**对话记录**，以及**关键状态信息**，如短期计划、通过工具获得过的关键知识、访问过的网页等。 |
| **RAG（检索知识）** | **查询外部数据库或文档知识库**，将相关引用材料送入上下文，以提升输出准确性并控制"幻觉"。RAG 结果可以以 **User Prompt** 的形式存在上下文中，通常紧跟 System Prompt 之后，也可以以**工具调用（Tool Call）**的形式由模型自主决定检索的时机和查询条件（如关键词）及排序。 |
| **Long-Term Memory（长期记忆）** | 之前的**对话内容总结**、**个人偏好**、**长期信息**（例如你的项目、日程、偏爱）。同样长期记忆也是以 **User Prompt 或调用记忆检索工具**的形式送入上下文。和人类记忆一样，长期记忆也会有**"逐渐遗忘"**的特性，比如越近的对话记录就越详细（甚至是原文），而越早的则越精简。 |
| **Available Tools（工具链）** | 包括用于获得外部环境信息的工具，如数据库、搜索引擎以及上面提到的 RAG 和 Memory 检索工具；也包括用于影响外部环境的工具，如代码执行、文件操作等。 |
