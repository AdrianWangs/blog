## 概述

哈希表是 Redis 中最核心的数据结构之一，不仅用于实现 Redis 的字典（Dict）和哈希对象（Hash Object），还是 Redis 数据库键值对存储的基础设施。Redis 对哈希表进行了精心设计，在保证高性能查询的同时，通过链式哈希和渐进式 rehash 等机制优化了哈希冲突和扩容过程，极大地提升了 Redis 的整体性能和稳定性。

本文将深入剖析 Redis 哈希表的实现原理、结构设计、哈希冲突解决方案以及渐进式 rehash 机制，帮助你全面理解 Redis 内部的核心数据结构。

## 哈希表基础

### 什么是哈希表

哈希表是一种保存键值对（key-value）的数据结构。哈希表中的每一个 key 都是独一无二的，程序可以根据 key 查找到与之关联的 value，或者通过 key 来更新 value，又或者根据 key 来删除整个 key-value 等等。

哈希表最大的优势在于，它**能以 O(1) 的平均时间复杂度快速查询数据**。这是通过哈希函数实现的 - 将 key 通过哈希函数计算得到哈希值，从而定位数据在表中的位置。由于哈希表本质上是数组结构，所以可以通过索引值直接访问到数据。

### Redis 中哈希表的应用

在 Redis 中，哈希表主要用于以下几个方面：

1. **Redis 数据库的底层实现**：Redis 的每个数据库都由一个字典（Dict）实现，而字典底层就是哈希表
2. **Hash 类型的键**：Redis 的 Hash 对象在元素较多时使用哈希表实现
3. **集合（Set）类型的键**：当集合中包含字符串对象时，通常使用哈希表实现

> 注意：在 Redis 6.0 之前，Hash 对象的底层实现可能是压缩列表或哈希表；从 Redis 6.2 开始，压缩列表已被 listpack 数据结构所取代，提供了更好的内存效率和性能表现。

## 哈希表结构设计

Redis 的哈希表在源码中定义了两个关键结构：`dictht`（哈希表）和 `dictEntry`（哈希表节点）。

### 哈希表结构

```c
typedef struct dictht {
    // 哈希表数组
    dictEntry **table;
    // 哈希表大小
    unsigned long size;  
    // 哈希表大小掩码，用于计算索引值，等于 size-1
    unsigned long sizemask;
    // 该哈希表已有的节点数量
    unsigned long used;
} dictht;
```

哈希表本质上是一个数组（`dictEntry **table`），数组的每个元素是一个指向「哈希表节点」的指针。

### 哈希表节点结构

```c
typedef struct dictEntry {
    // 键值对中的键
    void *key;
  
    // 键值对中的值（联合体）
    union {
        void *val;     // 指针
        uint64_t u64;  // 无符号64位整数
        int64_t s64;   // 有符号64位整数
        double d;      // 双精度浮点数
    } v;
    
    // 指向下一个哈希表节点，形成链表
    struct dictEntry *next;
} dictEntry;
```

哈希表节点的设计有两个值得注意的点：

1. **链式结构**：每个节点都有一个 `next` 指针，可以将多个节点链接起来，形成链表，这是 Redis 解决哈希冲突的关键
   
2. **值的存储优化**：值被定义为联合体（union），可以存储不同类型的数据，包括：
   - 指向实际值的指针
   - 直接存储整数值（无符号或有符号的64位整数）
   - 直接存储浮点数

这种设计的好处是**节省内存空间**。当值是整数或浮点数时，可以直接内嵌在节点结构中，无需额外分配内存，从而提高内存使用效率。

### 字典结构

Redis 使用 `dict` 结构体来表示字典，它封装了哈希表的实现：

```c
typedef struct dict {
    // 类型特定函数
    dictType *type;
    
    // 私有数据
    void *privdata;
    
    // 两个哈希表，交替使用，用于 rehash 操作
    dictht ht[2]; 
    
    // rehash 索引，当 rehash 不在进行时，值为 -1
    long rehashidx;
    
    // 当前正在运行的安全迭代器数量
    int iterators;
} dict;
```

这里定义了**两个哈希表**（`ht[0]` 和 `ht[1]`），这是 Redis 实现渐进式 rehash 的基础，后文会详细解释。

## 哈希冲突与解决方案

### 什么是哈希冲突

哈希冲突是指两个或多个不同的 key，经过哈希函数计算后得到了相同的哈希值，从而映射到哈希表的同一个位置（同一个哈希桶）。

例如，在一个大小为 8 的哈希表中：
- key1 经过哈希计算后得到索引值 1
- key9 也经过哈希计算后得到索引值 1
- key10 经过哈希计算后得到索引值 6

此时，key1 和 key9 会被分配到同一个哈希桶中，这就产生了哈希冲突。

> 计算索引值的公式：`index = hash(key) & sizemask`
> 其中 sizemask 等于哈希表大小减一（size-1）

### 链式哈希解决方案

Redis 采用了「**链式哈希**」（也称为拉链法）来解决哈希冲突。当多个 key 被分配到同一个哈希桶时，它们会形成一个单向链表：

1. 每个哈希表节点都有一个 `next` 指针
2. 具有相同索引值的多个节点通过 `next` 指针连接成链表
3. 新节点会被添加到链表的头部（O(1) 操作）

例如，当 key1 和 key9 发生哈希冲突时，它们会形成这样的链表结构：
- 哈希桶 1 -> key9 -> key1 -> NULL

链式哈希的优点是实现简单，插入操作效率高；缺点是当链表变长时，查询性能会下降（最坏情况下时间复杂度为 O(n)）。

## rehash 触发条件

随着数据的增加，哈希冲突的概率会提高，链表会变长，影响查询性能。为了保持哈希表的高效，Redis 会在适当的时候对哈希表进行扩容，这个过程称为 rehash。

rehash 的触发条件与**负载因子（load factor）**有关。负载因子计算公式为：

```
负载因子 = 哈希表已保存节点数量 / 哈希表大小
```

Redis 触发 rehash 的条件主要有两个：

1. **当负载因子大于等于 1，并且 Redis 没有在执行 BGSAVE 命令或 BGREWRITEAOF 命令时**
   - 即当哈希表节点数量等于或超过哈希表大小，且没有进行 RDB 快照或 AOF 重写操作时
   - 这是为了避免 rehash 和持久化同时进行导致的性能问题

2. **当负载因子大于等于 5 时**
   - 无论 Redis 是否正在执行持久化操作
   - 此时表示哈希冲突已经非常严重，必须强制进行 rehash

> 通过这种设计，Redis 在保证性能的同时，也尽量避免了持久化操作和 rehash 操作同时进行带来的额外内存压力。

## rehash 过程

rehash 是哈希表扩容或缩容的过程。Redis 的 rehash 机制非常巧妙，下面我们来看看它的实现。

### 哈希表的扩容设计

前面提到，Redis 的字典结构中包含两个哈希表：`ht[0]` 和 `ht[1]`。在正常情况下，所有数据都存储在 `ht[0]` 中，而 `ht[1]` 只有在 rehash 时才会使用。

![Redis 哈希表结构](https://img-blog.csdnimg.cn/img_convert/2fedbc9cd4cb7236c302d695686dd478.png)

### 标准 rehash 步骤

完整的 rehash 过程分为三步：

1. **分配空间**：为 `ht[1]` 分配空间
   - 扩容时，`ht[1]` 的大小通常是 `ht[0]` 大小的两倍
   - 缩容时，`ht[1]` 的大小通常是 `ht[0]` 大小的一半

2. **数据迁移**：将 `ht[0]` 中的所有数据重新计算哈希值，然后迁移到 `ht[1]` 中

3. **角色互换**：迁移完成后
   - 释放 `ht[0]` 的空间
   - 将 `ht[1]` 设置为 `ht[0]`
   - 创建新的空白 `ht[1]`，为下次 rehash 做准备

如图所示：

![rehash 过程](https://img-blog.csdnimg.cn/img_convert/cabce0ce7e320bc9d9b5bde947b6811b.png)

### 标准 rehash 的问题

标准 rehash 过程存在一个明显的问题：**当哈希表中的数据量很大时，一次性将所有数据迁移到新表会导致 Redis 出现明显的卡顿**。

例如，如果哈希表中有数百万个键值对，一次性迁移可能会导致 Redis 服务在一段时间内无法响应请求，这对于要求高可用性的场景是不可接受的。

## 渐进式 rehash

为了解决标准 rehash 可能导致的服务阻塞问题，Redis 采用了**渐进式 rehash**策略，将迁移过程分散到多次操作中完成。

### 渐进式 rehash 步骤

1. **分配空间**：与标准 rehash 一样，为 `ht[1]` 分配空间

2. **分散迁移**：在渐进式 rehash 进行期间，每次进行增删改查操作时：
   - 执行对应的操作
   - **额外顺序迁移一部分 `ht[0]` 中的数据到 `ht[1]`**
   - 使用 `rehashidx` 标记迁移进度，初始值为 0，表示开始迁移

3. **定时任务辅助**：Redis 的定时任务会在空闲时间帮助执行 rehash

4. **完成迁移**：当所有数据都迁移完成后
   - 释放 `ht[0]` 空间
   - 将 `ht[1]` 设置为 `ht[0]`
   - 重置 `rehashidx` 为 -1，表示 rehash 完成

### 渐进式 rehash 的特点

渐进式 rehash 期间，Redis 具有以下特点：

1. **双表并存**：数据同时存在于 `ht[0]` 和 `ht[1]` 两个表中
   - 查找时会先查 `ht[0]`，未找到再查 `ht[1]`
   - 新增数据只会添加到 `ht[1]`
   - 确保 `ht[0]` 的数据只减不增

2. **迁移成本分摊**：将一次大规模迁移操作分散为多次小规模操作
   - 每次操作只迁移几个哈希桶
   - 避免了服务暂停或明显延迟
   - 用户感知不到 rehash 过程

3. **自适应速度**：迁移速度与请求量相关
   - 请求越多，迁移越快
   - 系统负载小时，定时任务也会推进 rehash

通过渐进式 rehash，Redis 巧妙地解决了扩容过程中的性能问题，保证了服务的高可用性。

## 实际应用案例

### 字典实现

Redis 的数据库就是使用字典来存储键值对，键是数据库的键，值则是数据库的值。当执行以下命令时：

```
SET user:1 "James"
```

Redis 会在数据库的字典中新增一个键值对，键是字符串对象 "user:1"，值是字符串对象 "James"。

### 哈希对象实现

当使用 Redis 的 Hash 数据类型存储大量数据时，底层就会使用哈希表实现：

```
HSET user:1 name "James" age 35 city "Beijing"
```

这个命令会创建一个哈希对象，内部使用哈希表存储多个键值对。

### 性能表现

得益于哈希表的高效实现，Redis 能够在海量数据环境下依然保持优秀的性能：

- 在负载因子控制合理的情况下，大多数操作的时间复杂度为 O(1)
- 即使在千万级别的数据量下，单个查询操作仍能保持微秒级响应

## 总结

Redis 哈希表是其高性能的核心基础，通过精心的设计实现了以下优势：

1. **高效的数据访问**：利用哈希函数实现 O(1) 时间复杂度的数据访问
2. **优雅的冲突解决**：通过链式哈希解决哈希冲突
3. **智能的动态扩容**：基于负载因子自动触发 rehash
4. **平滑的扩容过程**：渐进式 rehash 避免服务中断
5. **高效的内存使用**：联合体设计节省内存空间

Redis 哈希表的实现体现了其设计者在性能和可用性之间的精妙平衡，这也是 Redis 能够在众多 NoSQL 数据库中脱颖而出的重要原因之一。

理解 Redis 哈希表的工作原理，有助于我们更好地使用 Redis，优化应用性能，并在设计自己的系统时汲取其中的精髓。
